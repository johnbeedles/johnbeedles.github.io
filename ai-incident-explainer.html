Project Overview

Modern systems fail in cryptic ways. A blockchain transaction reverts silently. A payment API returns a 402 with a decline code that means nothing without context. A 429 floods the logs at 9am and no one knows why it started. In all three cases the raw error is technically correct but practically useless to everyone except the engineer who wrote the API.

The AI Incident Explainer bridges that gap. It accepts any raw error - JSON responses, HTTP logs, smart contract revert strings, stack traces - runs it through an AI analysis chain, and returns a structured breakdown: what happened, why it happened, what to do, and how confident the system is in that diagnosis. The output is designed to be immediately actionable, suitable for sharing with a user, pasting into a post-incident review, or using as a starting point for deeper investigation.

Why This Was Built

Support engineers and developers spend a significant amount of time decoding errors that are technically accurate but communicate nothing useful. A raw 429 Too Many Requests tells you what happened at the HTTP layer. It does not tell you whether the cause is a polling loop, an N+1 query pattern, a missing cache, or a sudden spike in user activity - and it certainly does not tell you what to do about it.

This tool was built to demonstrate how language models can be integrated into a real support workflow - not as a chatbot, but as a structured analysis engine with a consistent, typed output contract. The design mirrors how I approach real incidents: identify the plain-English summary first, then the specific technical cause, then the blast radius, then concrete next steps. The AI makes that structure available on demand, for any error, in under two seconds.

A secondary goal was to build something directly relevant to roles in AI support engineering - demonstrating LLM API integration, prompt engineering, and the ability to think about AI output as a typed data contract rather than free-form text.

Tech Stack - Decisions and Rationale

Each technology in the stack was chosen for a specific reason, not just familiarity.

FastAPI

FastAPI handles HTTP routing, request and response validation via Pydantic, and serves the frontend HTML as a static file. It was chosen over Flask for its native async support, automatic OpenAPI documentation at /docs, and first-class Pydantic integration - which means the API contract is enforced at the framework level, not in ad-hoc validation code. The interactive docs at /docs also make the API immediately demonstrable without a frontend.

LangChain - StructuredOutputParser and LCEL

LangChain's StructuredOutputParser is the core architectural decision. It accepts a list of ResponseSchema objects - one per output field - and automatically generates the format instructions that are appended to every prompt. This eliminates the need to manually craft JSON schema instructions and handles parsing edge cases where the model slightly mis-formats its output. The chain follows the LangChain Expression Language (LCEL) pattern, connecting components with the pipe operator:

ChatPromptTemplate  →  ChatOpenAI (gpt-4o-mini)  →  StructuredOutputParser  →  Python dict

The chain is built once at application startup and reused for every request, avoiding re-initialisation overhead on each call. The model runs at temperature=0.2 for consistent, factual output across repeated runs on identical inputs.

OpenAI GPT-4o-mini

GPT-4o-mini was selected over the full GPT-4o model for this use case because the task - classifying and explaining a bounded error input - does not require the reasoning depth of the larger model. The smaller model responds faster, costs significantly less at scale, and at temperature=0.2 produces output quality that is functionally identical for structured classification tasks. For a production deployment this would also make the tool viable to run at high request volume without cost constraints.

Pydantic - Request and Response Contracts

Every request and response is defined as a Pydantic model. The AnalyseRequest model validates incoming payloads; the AnalyseResponse model shapes the outgoing data. This means the LLM output is never passed raw to the client - it is re-typed through a Pydantic model that rejects malformed fields, coerces types, and guarantees a stable interface. Edge cases where the model returns suggestedFix as a plain string rather than an array are caught and re-parsed before the response is constructed.

How It Was Built - Step by Step

The build followed a deliberate sequence - output schema first, then the AI chain, then the API wrapper, then the frontend.

Step 1 - Define the Output Schema

Before writing any code, the output contract was defined: what fields does a useful incident analysis need to contain? The schema settled on ten fields - explanation, rootCause, category, severity, suggestedFix, confidence, confidenceReason, docLinks, beforeSummary, and afterSummary. Defining the output first meant the prompt could be engineered to produce exactly those fields, rather than retrofitting structure onto whatever the model naturally returned.

Step 2 - Build the LangChain Chain

Each output field was defined as a ResponseSchema object with a name and description. The StructuredOutputParser consumes these schemas and generates format instructions automatically. The system prompt instructs the model to act as a senior incident response engineer, specifies valid values for enumerated fields (severity must be P1/P2/P3/P4; category must be one of nine defined types), and sets the analytical tone - precise, actionable, no jargon in the user-facing explanation layer.

Step 3 - Wrap in a FastAPI Endpoint

The POST /analyse endpoint accepts a Pydantic AnalyseRequest model, invokes the LangChain chain with the error input and format instructions, handles edge cases in the parsed output, and returns a fully typed AnalyseResponse. An elapsed_ms field is included in every response for latency visibility. A GET /health endpoint exposes the model name and chain type for monitoring. FastAPI's auto-generated /docs interface provides a built-in test harness.

Step 4 - Build and Serve the Frontend

The frontend is a single HTML file with embedded CSS and JavaScript, served directly by FastAPI via FileResponse("frontend/index.html"). It requires no build step, no npm, and no framework. JavaScript makes a standard fetch() call to POST /analyse and renders the JSON response into labelled output cards. Four pre-loaded example incidents - covering Web3, Stripe, REST rate limiting, and JWT authentication - allow the tool to be demonstrated instantly without needing real errors.

Step 5 - Local Setup

  • Create and activate a Python virtual environment: python -m venv venv && source venv/bin/activate
  • Install dependencies: pip install -r requirements.txt
  • Copy the environment template and add your OpenAI key: cp .env.example .env
  • Start the server: python main.py
  • Open the app at http://localhost:8000 - API docs available at /docs

Example Use Cases

Three real-world style incidents that demonstrate the breadth of the tool - covering blockchain, payments, and REST API failure patterns.

Use Case 1 - Web3 / Smart Contract Revert (ERC-20 Allowance)

A user tries to spend USDC tokens via a DeFi protocol and the transaction fails on-chain. They raise a support ticket with only a transaction hash. The raw revert message is pasted into the tool.

Input - Raw Error

Transaction Hash: 0x7f3a9b2c1d4e5f6a7b8c9d0e1f2a3b4c Status: FAILED Error: execution reverted: ERC20: transfer amount exceeds allowance Contract: 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48 (USDC) Function: transferFrom(address from, address to, uint256 amount) Amount: 500000000 (500 USDC) Network: Ethereum Mainnet

Tool Output

  • Explanation: The transaction tried to move USDC tokens on behalf of the user, but the user had not pre-approved this contract to spend their tokens. No tokens moved and gas was consumed because the revert happened during execution.
  • Root Cause: Missing approve() call. The transferFrom() function requires the token owner to explicitly grant an allowance to the spender address before the transfer can proceed.
  • Suggested Fix: Call approve(spenderAddress, amount) on the USDC contract from the user's wallet, verify the allowance is sufficient using allowance(owner, spender), then retry the transaction.
  • Severity: P4 - single-user impact, no platform issue. Confidence: HIGH - the revert string is unambiguous.

In a Trust Wallet or DeFi support context, this is one of the most common user-facing failures. Being able to translate a raw revert string into clear, step-by-step user guidance demonstrates both Web3 technical knowledge and support communication skills.

Use Case 2 - Stripe Payments API / Card Declined

A merchant's checkout is failing for some customers. The developer pastes the raw Stripe error response into the tool, unsure whether the issue is in their integration or on the card side.

Input - Raw Error

{ "error": { "code": "card_declined", "decline_code": "insufficient_funds", "message": "Your card has insufficient funds.", "payment_intent": { "id": "pi_3N9xKmP3eZvKYlo2", "amount": 5000, "currency": "usd", "status": "requires_payment_method" }, "type": "card_error" } }

Tool Output

  • Explanation: The customer's card was declined by their bank due to insufficient funds. Stripe processed the request correctly - this is a card-side rejection, not an integration error.
  • Root Cause: type: "card_error" confirms the integration worked. The decline originated at the issuing bank. decline_code: "insufficient_funds" is unambiguous.
  • Suggested Fix: Prompt the customer to use a different payment method. Check the Stripe Dashboard for decline code patterns across transactions. Implement retry logic with a clear user-facing message that distinguishes card errors from integration errors.
  • Severity: P4 - affects individual transactions, not the overall system. Confidence: HIGH.

The key insight is knowing that type: "card_error" means the integration worked. A support engineer who makes this distinction immediately prevents unnecessary escalation to the development team.

Use Case 3 - REST API Rate Limit / Production Degradation

An internal dashboard stops loading at 9am on a Monday. The on-call engineer checks the logs and sees a flood of 429 responses from a third-party data API. A representative log entry is pasted into the tool to begin triage.

Input - Raw Error

[ERROR] 2024-01-15 09:03:44 UTC GET https://api.dataservice.com/v2/analytics/report Status: 429 Too Many Requests Headers: Retry-After: 60 X-RateLimit-Limit: 100 X-RateLimit-Remaining: 0 Body: { "error": "rate_limit_exceeded", "message": "You have exceeded your 100 req/min limit." } Occurred: 47 times in last 60 seconds

Tool Output

  • Explanation: The application sent over 100 requests to the data API in under a minute, hitting the provider's rate cap. The service degraded as a result - requests are being rejected until the window resets.
  • Root Cause: No request throttling or caching in place. Likely a polling loop or N+1 query pattern firing on peak Monday morning load. The X-RateLimit-Remaining: 0 header confirms the limit was fully exhausted.
  • Suggested Fix: Implement exponential backoff respecting the Retry-After: 60 header. Add a caching layer to de-duplicate repeat calls within the rate window. Review polling interval and request batching strategy to stay within 100 req/min under peak load.
  • Severity: P2 - service degraded but not fully down. Dashboard users are impacted. Needs immediate mitigation. Confidence: HIGH.

Rate limit incidents are one of the most common real-world API failures. Understanding that the fix is architectural - caching and backoff - rather than simply retrying faster, is the mark of a senior support or platform engineer.

Key Takeaways

The most valuable aspect of this project is not the AI integration - it is the understanding of what a good incident analysis looks like. The output schema (explanation → root cause → category → severity → fix → confidence) mirrors exactly how I structure real incident triage: start with the plain-English summary for stakeholders, identify the specific technical cause, assess blast radius, then give the team concrete next steps.

Building this required knowing what each error type actually means - not just that a 429 is a rate limit, but that the Retry-After header is the first thing to inspect, that the architectural fix is usually a cache rather than a slower retry, and that the 47 occurrences in 60 seconds is the signal pointing to a loop rather than organic traffic. The AI makes that knowledge accessible consistently and at speed. The engineering behind it makes it reliable.

One broader point: integrating a language model into a support workflow only works if the output is structured and typed - not free-form text. The StructuredOutputParser approach used here is the pattern that makes AI output safe to render in a UI, log to a database, or pipe into a downstream automation. That design decision is more important than the model choice.
