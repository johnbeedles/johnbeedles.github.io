About This Guide

Supporting blockchain platforms introduces failure patterns that don't exist in traditional software support: transactions that are irreversible, finality delays that are by design, multi-chain environments where the same address means different things depending on context, and on-chain state that is independently verifiable via block explorers.

This reference organises those failure patterns by category, with step-by-step identification and resolution guidance for each. It reflects the kind of structured investigation approach I apply to on-chain support cases - always establishing the layer of failure before acting, and always gathering on-chain evidence before escalating or advising.

The focus throughout is operational accuracy over speed: validating chain state, isolating the failure layer, correlating API behaviour with on-chain evidence, and avoiding remediation steps that could increase financial risk or create duplicate transactions.

Key Concepts

  • Transaction lifecycle: sign → broadcast → validate → include → confirm → finalise
  • Gas: base fee + priority tip; limit vs price distinction
  • Finality: Ethereum requires 2/3 supermajority validator attestation (~66.7%)
  • USDC: 6 decimal places on EVM chains (1 USDC = 1,000,000 raw units)

Transaction Pending

A pending transaction has been broadcast to the network but not yet included in a confirmed block. The cause determines whether the user needs to act or simply wait. Always check the block explorer first to confirm the transaction has been broadcast at all - a transaction with no explorer record has a different root cause entirely (RPC or broadcast failure).

Low Gas Price Set by User

Identify

  • Get the transaction hash from the customer and look it up on the relevant block explorer
  • Check the gas price paid and compare it against the current network base fee
  • Confirm the status shows Pending - not Failed
  • Ask whether the customer set a custom gas price manually
  • Check whether another pending transaction with a lower nonce is blocking confirmation - nonce gaps commonly cause later transactions to remain pending even when gas pricing is sufficient

Resolve

  • Advise the customer to use their wallet's speed up function
  • If no speed-up option is available, submit a replacement transaction with the same nonce
  • For API-submitted transactions, resubmit with a higher fee configuration
  • Confirm the replacement transaction is accepted and the original is dropped from the mempool
  • If using multiple RPC providers, confirm the replacement transaction has propagated consistently across nodes — mempool state can differ temporarily between providers

Network Congestion

Identify

  • Check a gas tracker and compare current base fee levels
  • Check mempool backlog size
  • Confirm whether multiple customers are reporting delays
  • Review chain status pages for infrastructure incidents

Resolve

  • Explain this is a network-level condition
  • Advise waiting if the use case is not time-sensitive
  • Recommend dynamic gas pricing for future integrations
  • Use replacement transactions only when urgency justifies it

Validator Delays

Identify

  • Compare recent block timestamps against normal cadence
  • Check official status pages and validator incident reports
  • Confirm the transaction exists on-chain
  • Check whether delays affect multiple users and wallets

Resolve

  • Explain this is external infrastructure outside platform control
  • Monitor recovery rather than immediately resubmitting
  • Re-broadcast through another RPC provider if necessary
  • Escalate internally if platform-operated infrastructure is also degraded
  • When escalating internally, include transaction hashes, affected chain IDs, timestamps, RPC providers, correlation IDs, and customer impact summary to accelerate engineering investigation

Transaction Failed

A failed transaction has been broadcast, reached the chain, and been rejected at execution time. Unlike a pending transaction, a failed status is final for that submission and will not retry automatically.

Invalid Parameters

Identify

  • Review API request payloads and calldata carefully
  • Check structured validation responses from the API
  • Verify address format and checksum validation
  • Confirm chain ID alignment between wallet and network
  • Review request correlation IDs, API logs, and webhook delivery logs to confirm whether the request failed during validation, asynchronous processing, or downstream reconciliation

Resolve

  • Map the validation failure to the offending parameter
  • Verify token decimal precision is correct
  • Recommend client-side validation before submission
  • Resubmit using a new idempotency key
  • If webhooks are involved, confirm the customer is validating webhook signatures and handling retry events idempotently to avoid duplicate processing

Wrong Network

Wrong network errors are among the most disorienting for customers because the transaction often succeeds technically — the funds arrive somewhere, just not where intended.

Testnet Address or Credentials Used in Production

Identify

  • Confirm whether sandbox or production credentials were used
  • Compare balances across mainnet and testnet explorers
  • Verify chain IDs and configured environments
  • Review deployment configuration and environment variables

Resolve

  • Confirm the customer has completed production onboarding
  • Ensure the correct production API base URL is being used
  • Replace hardcoded testnet values with production equivalents
  • Recommend environment-variable based configuration management

Confirmation Delays

Confirmation delays occur after a transaction has been included in a block but before downstream systems recognise it as final.

Network Congestion at the Confirmation Layer

Identify

  • Verify the transaction has a block number
  • Compare accumulated confirmations against platform thresholds
  • Compare current block times against normal cadence
  • Confirm whether delays affect multiple users

Resolve

  • Reassure the customer the transaction has been included on-chain and is progressing through confirmations. While short-lived reorganisations are possible before finality, transactions that continue accumulating confirmations are generally considered secure.
  • Provide estimated completion time based on current block speed
  • Explain that confirmation accumulation is automatic
  • Recommend higher gas priority during congestion windows

Key Principles for Blockchain Support

Blockchain support differs from traditional software support in one fundamental way: the chain itself is the source of truth, while block explorers provide a readable representation of that state. Before forming any hypothesis, the first action is always to look up the transaction hash and establish what the chain actually recorded — not what the customer believes happened, and not what the application layer reported.

The second consistent theme across these failure patterns is the importance of layer identification before action. Is the issue at the API layer, broadcast layer, validation layer, execution layer, or confirmation layer?

Finally: irreversibility changes the stakes. A mis-directed transaction cannot be recalled, and gas spent on failed execution is not refunded. In blockchain support, advising customers to act before the root cause is understood carries real financial risk.
