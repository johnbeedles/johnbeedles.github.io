Case Study: API Debugging
Failed Payment Request

A production investigation into intermittent merchant-specific payment API failures — isolating the root cause through payload comparison, distributed trace analysis, and log correlation, then driving the engineering fix and monitoring improvements that eliminated recurrence.

Project Overview

During peak processing hours, approximately 2% of payment transactions from a subset of enterprise merchants began returning errors at the API layer. The failures were silent from the merchant's perspective — their systems received a generic error with no actionable detail. I led the investigation from initial alert through to root cause, coordinated the engineering fix, and owned the improvements to error messaging and monitoring that ensured this class of failure would be caught and communicated clearly in the future.

Investigation

Alert triggered for elevated 422 error rate on the payment submission endpoint during peak processing. Approximately 2% failure rate across a subset of merchants — no impact on the broader platform, but significant for the affected clients.

Steps Taken

  • Acknowledged alert and opened incident bridge. Immediately filtered Splunk logs by endpoint, HTTP status code, and enterpriseID — confirming within minutes that the 422 errors were concentrated in three specific enterprise accounts, not platform-wide.
  • Cross-referenced Dynatrace service maps and distributed traces to locate the point of failure. Traces showed requests reaching a downstream validation service and returning 422 Unprocessable Entity, but the upstream response to merchants was being translated into a generic 500 with no detail — a compounding issue that made merchant-side diagnosis impossible.
  • Pulled a sample of failing requests from logs. To safely reproduce the issue, I constructed sanitised Postman requests using anonymised test values for maskedPAN and onlineToken, while preserving the exact structure of the merchantTransactionID field from the failing payloads. Sensitive card and customer data was not used in reproduction at any stage.
  • Reproduced the 422 consistently. Began systematically comparing the failing merchantTransactionID values against successful ones from the same endpoint. Identified the pattern: failing merchants were generating merchantTransactionID values with special characters (specifically hyphens and underscores in combination) and lengths exceeding the validation service's undocumented field constraints.
  • Confirmed via trace analysis that the validation service was correctly rejecting these values but returning an error that was not being propagated cleanly — the upstream service swallowed the detail and returned a 500 to the merchant with no indication of the offending field.
  • Reviewed salesDetails and purchaseAmount fields across both failing and successful requests to rule out additional contributing factors — no anomalies found; the issue was isolated entirely to merchantTransactionID format handling.
  • Checked whether clientID correlated with the failure pattern — it did, confirming that three specific integration configurations shared the same ID generation logic producing the non-conforming values.

Root Cause

The downstream validation service rejected merchantTransactionID values containing specific special character combinations (hyphen + underscore) and values exceeding an undocumented maximum length. This caused a 422 Unprocessable Entity at the validation layer.

Two compounding issues made this harder to detect and resolve quickly:

  • Error propagation failure: The upstream payment service was translating the validation layer's 422 into a generic 500, stripping all detail. Merchants received no indication of which field was rejected or why.
  • Undocumented constraints: The merchantTransactionID field constraints were not documented in the integration guide or API schema, meaning merchants had no reference point for valid formats — making this a platform issue, not a merchant error.

Resolution & Improvements

  • Immediate: Worked directly with the three affected merchants to provide interim field formatting guidance, unblocking their transactions within the same business day.
  • Validation logic: Raised a Jira ticket with a full reproduction case, payload examples, and proposed fix. Engineering updated the validation service to handle the edge case formats while preserving security constraints, and added input sanitisation for field length.
  • Error propagation: Drove a fix to ensure 422 responses from the validation layer are surfaced with full field-level detail to the calling service and ultimately to the merchant — replacing the generic 500 with a structured error referencing the offending field and the expected format.
  • API documentation: Coordinated with the technical writing team to document merchantTransactionID format constraints in the integration guide, with valid and invalid examples.
  • Monitoring: Added a dedicated Splunk alert for elevated 422 rates on this endpoint, broken down by enterpriseID, enabling faster triage and merchant-level scoping for future issues.
  • Contract testing: Advocated for and agreed with engineering that contract tests be added for merchantTransactionID validation to prevent silent regressions from future validation service changes.
  • Runbook: Authored a runbook for this error pattern, including Splunk query templates, field-level payload comparison steps, and the Postman reproduction workflow using anonymised data.
  • Outcome: No further occurrences of this error pattern were observed following the fix, and merchant-facing error clarity improved significantly.

Key Takeaways

This case had two separate problems: the root cause itself (undocumented field constraints) and the thing that made it hard to find (error swallowing). In high-volume payment environments, poor error propagation between services is often as damaging as the underlying bug — it delays diagnosis, frustrates merchants, and erodes confidence in the platform. Fixing both is equally important.

One thing I would advocate for earlier in future: field-level validation constraints should be part of the API contract and tested at integration time — not discovered through production failures. The contract testing improvement was the right long-term fix, but it should have been in place before this feature shipped.
