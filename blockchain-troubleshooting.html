About This Reference

"Failed transaction" and "missing funds" reports are among the most common - and most misunderstood - issues in crypto and Web3 support. The same symptom can have a dozen different root causes, each requiring a different diagnostic approach and a different resolution. This guide documents the structured methodology I apply to each failure class, covering identification, triage, and resolution steps with the precision expected at senior level.

What This Demonstrates

  • Structured, repeatable diagnostic methodology for on-chain failures
  • Depth of knowledge across EVM transaction lifecycle, gas mechanics, and finality
  • Ability to triage quickly using block explorers, gas trackers, and trace tools
  • Clear separation between user error, integration error, and chain-level conditions
  • Communication approach: setting expectations and explaining complex behaviour plainly

Failure Categories Covered

  • Transaction Pending - low gas price, network congestion, validator delays
  • Transaction Failed - insufficient funds, contract revert, gas exhaustion, invalid parameters
  • Wrong Network - chain mismatch, testnet/production environment errors
  • Confirmation Delays - congestion at confirmation layer, validator issues, reorg protection

Tools & Methods Referenced

  • Etherscan, Basescan, Polygonscan (block explorers)
  • Tenderly (transaction simulation & trace)
  • Etherscan Gas Tracker, Blocknative (mempool & gas)
  • eth_estimateGas, eth_gasPrice (RPC methods)
  • EIP-1559 fee model & mempool replacement rules
  • ERC-20 allowance model, ERC-4337 account abstraction

Transaction Pending

A transaction in the pending state has been broadcast to the network but not yet included in a block. The cause determines whether action is needed - and how urgently.

⛽

Low gas price set by user

on-chain user config
Identify
  • 1Get the transaction hash from the customer and look it up on the relevant block explorer (Etherscan, Basescan, Polygonscan, etc.)
  • 2Check the gas price paid on the transaction detail page and compare it against the current network base fee using a gas tracker (e.g. Etherscan Gas Tracker)
  • 3Confirm the transaction status shows Pending - not Failed - which distinguishes a queued transaction from a reverted one
  • 4Ask the customer which wallet or integration submitted the transaction and whether they set a custom gas price manually rather than using the wallet's recommended estimate
Resolve
  • 1Advise the customer to use the Speed Up function in their wallet (MetaMask, Rabby, etc.) - this resubmits the transaction at a higher gas price using the same nonce, replacing the stuck one
  • 2If no speed-up option exists, they can submit a zero-value self-transfer to their own address with the same nonce and a higher gas price - this cancels and replaces the pending transaction
  • 3For programmatically submitted transactions, resubmit with an updated maxFeePerGas (EIP-1559) or gasPrice (legacy) at least 10% higher than the original - the minimum increment required for a replacement to be accepted by the mempool
  • 4Confirm the replacement transaction is mined and the original is dropped from the mempool - the block explorer and wallet should both reflect the updated status
📈

Network congestion

on-chain external
Identify
  • 1Check a gas tracker (Etherscan Gas Tracker, Blocknative) - confirm the network base fee is elevated versus the gas price the customer paid
  • 2Check the mempool size - a large backlog of pending transactions confirms network congestion rather than a configuration error on the customer's side
  • 3Check whether other customers are reporting the same delay on the same chain - broad impact raises triage priority and shifts the root cause to external
  • 4Check the platform or chain status page for any active incidents or elevated congestion notices affecting that network
Resolve
  • 1Inform the customer this is a network-level condition, not a wallet or platform issue - set realistic expectations about resolution timeline
  • 2Advise them to wait if the use case is not time-sensitive - congestion typically resolves within minutes to a few hours as demand normalises
  • 3If urgent, advise using the speed-up / replace flow with a gas price at or above the current recommended fast level from the gas tracker
  • 4For future transactions, recommend enabling dynamic gas pricing in their integration (e.g. EIP-1559 fee estimation) rather than hardcoding a gas value
🖥️

Validator delays

on-chain infrastructure
Identify
  • 1Check the block explorer - is block production slowing down or stopping? Compare recent block timestamps against the chain's normal block cadence
  • 2Check the chain's official status channels (e.g. Ethereum Foundation blog, Base status page, respective Discord/X accounts) for reported validator or consensus layer incidents
  • 3Confirm the transaction has been broadcast and is visible in the mempool - if not appearing on the explorer at all, the issue may be at the RPC broadcast layer, not validators
  • 4Review whether transactions across multiple different senders are stuck - chain-wide impact confirms a validator issue rather than an isolated configuration problem
Resolve
  • 1Set customer expectations clearly - validator delays are external infrastructure issues outside the platform's control, dependent on the chain's own recovery
  • 2Monitor block production - once validators recover, pending transactions process in order based on gas price, with no customer action typically required
  • 3If the transaction was submitted via an RPC endpoint, try rebroadcasting via a different RPC provider (Alchemy, Infura, QuickNode) in case the original node is degraded or lagging
  • 4Escalate internally if any platform-operated infrastructure (RPC nodes, indexers, attestation services) is impacted alongside the validator issue

Transaction Failed

A failed transaction has been included in a block but reverted during execution - gas is consumed regardless. The revert reason is the primary diagnostic signal. Each failure class has a distinct cause and a distinct fix.

👛

Insufficient funds

wallet user error
Identify
  • 1Look up the wallet address on the block explorer and check its current token balance (e.g. USDC) and native gas token balance (ETH, MATIC, SOL, etc.) separately
  • 2Confirm the transaction failure reason - the explorer should show "Fail" with a revert reason or a pre-execution rejection indicating insufficient balance
  • 3Determine whether funds are missing for the transfer amount, the gas fee, or both - these are distinct balances; holding USDC does not cover ETH gas costs
  • 4If the transaction involves a fiat on-ramp or minting step, confirm the upstream deposit was fully settled before the on-chain action was attempted
Resolve
  • 1If the token balance is short: advise the customer to top up their wallet with the required amount before retrying
  • 2If the native gas token is short: the customer must fund the wallet with ETH, MATIC, or the relevant gas token - stablecoins alone cannot pay gas on standard EVM chains
  • 3If the platform uses gas abstraction or a paymaster (e.g. ERC-4337 account abstraction), verify the gas policy is correctly configured so end-users don't need to hold native tokens
  • 4Once funded, advise the customer to retry the transaction - if the platform uses idempotency keys, a new key must be issued for the retry
📄

Smart contract revert

smart contract on-chain
Identify
  • 1Find the transaction on the block explorer - look for the revert reason string in the transaction detail (e.g. "ERC20: transfer amount exceeds allowance", "Ownable: caller is not the owner")
  • 2If the revert reason is ABI-encoded hex, use a decoder tool such as Tenderly or Etherscan's built-in decoder to extract the human-readable error message
  • 3Identify which contract and function triggered the revert - was it the token contract, the platform's own contract, or the customer's integration contract?
  • 4Check whether a required ERC-20 token approval (allowance) step was skipped - contracts cannot transfer tokens on a user's behalf without an explicit prior approve() call
Resolve
  • 1Share the decoded revert reason with the customer - most standard revert strings are self-explanatory and map directly to a fixable integration issue
  • 2If the revert is an allowance error: the customer must call approve(spenderAddress, amount) on the token contract before the transfer call - this is a deliberate two-transaction ERC-20 design
  • 3If the revert originates inside a platform contract, escalate with the transaction hash, decoded revert reason, and chain ID - this may indicate a contract bug or access control misconfiguration
  • 4Advise the customer to simulate the corrected transaction using Tenderly before resubmitting, to confirm the fix works without spending additional gas on another failure
🔥

Gas exhausted (out-of-gas)

gas limit configuration
Identify
  • 1On the block explorer, check Gas Used vs Gas Limit on the failed transaction - if gas used equals the gas limit exactly, the transaction ran out of gas mid-execution
  • 2Distinguish an out-of-gas failure from a logic revert - both show as "Failed", but out-of-gas consumes the full gas limit while a logic revert typically returns unused gas
  • 3Ask whether the customer set a custom gas limit manually, or relied on an eth_estimateGas RPC call - estimates can under-predict for state-heavy operations
  • 4Check whether the contract being called was recently upgraded or has complex logic - changes that increase computation or storage writes require a higher gas limit than before
Resolve
  • 1Advise the customer to increase the gas limit - apply a 20–50% buffer above the eth_estimateGas return value, since estimates can fall short for complex state changes
  • 2Recommend calling eth_estimateGas with the exact calldata and sender address before each submission - this gives a more accurate baseline than a hardcoded value
  • 3If the integration uses a paymaster or gas abstraction layer, verify the gas policy ceiling is high enough to accommodate the operation's actual consumption
  • 4Retry with the corrected gas limit - the original failed transaction cannot be recovered and gas paid is not refunded, as the network performed work up to the point of exhaustion
⚠️

Invalid parameters

API / integration user error
Identify
  • 1Review the API request payload or transaction calldata - look for malformed addresses, incorrect token decimal values, or missing required fields
  • 2Check the API error response body - well-formed APIs return structured 400-series errors with field-level validation messages that pinpoint the exact problem
  • 3Verify the destination address format - EVM addresses are 42 hex characters (0x + 40 hex digits); Solana addresses are base58-encoded and a different length entirely
  • 4Confirm the chain ID in the request matches the chain the wallet and token actually exist on - submitting to the wrong chain ID is a common integration mistake
Resolve
  • 1Share the specific validation error message with the customer and map it to the relevant field in the API documentation
  • 2Verify USDC amounts use the correct decimal precision - USDC uses 6 decimals on EVM chains, so 1 USDC must be submitted as 1,000,000 in raw token units (not 18 decimals like ETH)
  • 3Advise the customer to validate inputs client-side before submission - including EVM address checksum validation (EIP-55) and amount sanity checks
  • 4Once corrected, resubmit with a new idempotency key if the platform uses them, to avoid a collision with the original failed request

Wrong Network

Chain and environment mismatches are the most common onboarding failure in Web3 support. Funds are rarely lost - but they require methodical identification to locate and recover.

🔀

Funds sent to address on wrong chain

chain mismatch user error
Identify
  • 1Ask the customer to confirm which chain they sent from and which chain the recipient was expecting - these are often assumed rather than verified
  • 2Look up the destination address on both chain explorers - if USDC arrived on Base but the recipient is checking Ethereum mainnet, the funds are present but on a different chain
  • 3Confirm whether the destination wallet or exchange supports the source chain - many centralised exchange deposit addresses only accept one specific network
  • 4Check whether the receiving platform auto-detects multi-chain deposits - some platforms credit cross-chain deposits automatically after a delay, making manual recovery unnecessary
Resolve
  • 1If the recipient controls the private key: they can connect their wallet to the correct chain - the same address exists across all EVM-compatible chains, so funds are accessible once the wallet is pointed at the right network
  • 2If the recipient is a centralised exchange: advise contacting the exchange's support team directly - many can manually credit cross-chain deposits, though this can take days and is not guaranteed
  • 3For future transfers, the customer should use an official cross-chain bridge (e.g. CCTP for USDC, or the destination chain's canonical bridge) rather than sending directly across chains
  • 4Advise the customer to always verify the network a deposit address supports before sending - on-chain transfers are irreversible once confirmed
🧪

Testnet credentials used in production

environment mismatch config error
Identify
  • 1Confirm which API environment the request was made against - check whether a sandbox or testnet API key was used when the customer intended to operate in production
  • 2Look up the wallet or contract address on both a mainnet and testnet block explorer - a balance or history appearing on Sepolia (chain ID: 11155111) but not mainnet (chain ID: 1) confirms an environment mismatch
  • 3Check the chain ID in the request payload - Ethereum mainnet is 1, Sepolia testnet is 11155111; a mismatch definitively confirms the wrong environment was targeted
  • 4Review the API base URL and credentials in the customer's configuration - sandbox and production environments use distinct API keys and base URLs that must not be mixed
Resolve
  • 1Confirm the customer has production API credentials - if they have only used a sandbox environment, they may need to complete onboarding steps before production access is granted
  • 2Ensure the correct production API base URL is configured - sandbox and production endpoints are different and must match the credentials being used
  • 3Audit the customer's config for hardcoded testnet chain IDs, contract addresses, or RPC endpoints - all must be replaced with mainnet equivalents before going live
  • 4Recommend using environment variables rather than hardcoded values throughout the integration - this prevents environment-specific config from bleeding across deployment stages

Confirmation Delays

Confirmation delays occur after a transaction has been successfully included in a block. The transaction is not lost - it is waiting for the platform's required confirmation threshold to be reached before funds are credited. Understanding the cause determines whether any action is possible.

⏸️

Network congestion (confirmation layer)

finality external
Identify
  • 1Verify the transaction has been included in a block - check the block explorer for a confirmed block number. If included, the delay is at the confirmation stage, not at broadcast
  • 2Check how many confirmations have accumulated versus the threshold required by the receiving platform - different platforms set different thresholds per chain
  • 3Compare the current block time against the chain's normal average - congestion can slow block production on some chains, extending the time between confirmations
  • 4Confirm whether the delay affects all transactions on that chain or just this one - chain-wide slow confirmations indicate congestion; an isolated delay may point to a different cause
Resolve
  • 1Reassure the customer that the transaction is permanently in the chain - once included in a block it cannot disappear, it is simply waiting for the required confirmation count
  • 2Set clear expectations - share the platform's confirmation threshold for that chain and an estimated wait time based on current block times
  • 3No action is required from the customer - confirmation accumulation is fully automatic once the transaction is in a block
  • 4For future high-priority transactions, advise setting a higher gas price during congestion periods to get faster block inclusion and start accumulating confirmations sooner
⚙️

Validator issues

consensus layer infrastructure
Identify
  • 1Check the chain's validator participation rate - Ethereum requires at least two-thirds (≥66.67%) of validators to attest for the chain to finalise; below this threshold, finality stalls
  • 2Check the chain's official status channels (Ethereum Foundation, Base status page, Arbitrum status page, etc.) for reported consensus layer incidents
  • 3Look at the block production rate on the explorer - significant gaps between blocks or a high rate of missed slots are indicators of validator participation issues
  • 4Confirm whether an internal incident has been raised for the affected chain - check whether any platform-operated RPC or indexing infrastructure is also impacted
Resolve
  • 1Communicate clearly to the customer that this is a chain-level issue outside the platform's control - share public status links so they can monitor progress independently
  • 2Monitor the chain - once validator participation recovers, finality resumes automatically and pending confirmations accumulate without customer action
  • 3If the outage is prolonged, assess whether an alternative supported chain is available for the customer's use case (e.g. Base or Arbitrum in place of Ethereum mainnet)
  • 4Escalate to engineering if any platform-operated infrastructure (RPC nodes, indexers, attestation services) is affected alongside the validator issue
🛡️

Reorg protection waiting periods

finality by design
Identify
  • 1Confirm the transaction has been included in a block but the downstream system (exchange, payment platform, custody provider) has not yet credited it
  • 2Check the receiving platform's required confirmation count for that chain - thresholds vary significantly by chain and platform (12 confirmations on Ethereum mainnet is a common standard; L2s typically require fewer)
  • 3Verify the current confirmation count on the block explorer and calculate how many remain - this allows you to give the customer a concrete estimated wait time based on current block cadence
  • 4Distinguish a waiting period from a genuine chain reorganisation - if the block containing the transaction has been replaced, the transaction returns to pending status and the block explorer will reflect this
Resolve
  • 1Explain to the customer that this is expected, intentional behaviour - confirmation thresholds exist to protect against chain reorganisations, which can reverse recently-included transactions on some chains
  • 2Provide the customer with the exact confirmation count required and an estimated time to completion based on current average block times for that chain
  • 3If a genuine reorg has occurred: the transaction will automatically reprocess once re-included in the canonical chain - manual resubmission is not required in most cases
  • 4For latency-sensitive use cases, advise evaluating chains with faster finality (Base, Arbitrum, Solana) where confirmation requirements and block times are lower by design

Key Takeaways

The most important triage skill in crypto support is resisting the urge to jump to a resolution before correctly identifying the failure class. "Gas consumed, no tokens received" is the symptom for at least five different root causes - each with a different explanation and a different fix. Getting this wrong erodes customer trust and wastes engineering time.

Two patterns come up repeatedly and are worth internalising: first, token balance and gas balance are completely separate - a wallet full of USDC can still fail to execute a transaction if it holds no ETH. Second, wrong-network deposits are rarely lost; they almost always require the recipient to connect their wallet to the correct chain, or to contact the exchange. Setting that expectation clearly and calmly is as important as the technical diagnosis itself.

Confirmation delays and reorg protection waiting periods are by design - not bugs. Being able to explain that distinction clearly, provide an exact confirmation count and estimated wait time, and communicate calmly under customer pressure is the mark of strong senior support.
