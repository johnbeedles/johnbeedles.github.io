On-Chain Failure Troubleshooting Guide

A practical support engineer reference covering the most common on-chain failure patterns — from pending and failed transactions through to wrong network errors and confirmation delays. About This Guide

Supporting blockchain platforms introduces failure patterns that don't exist in traditional software support: transactions that are irreversible, finality delays that are by design, multi-chain environments where the same address means different things depending on context, and on-chain state that is independently verifiable via block explorers.

This reference organises those failure patterns by category, with step-by-step identification and resolution guidance for each. It reflects the kind of structured investigation approach I apply to on-chain support cases - always establishing the layer of failure before acting, and always gathering on-chain evidence before escalating or advising.

What This Guide Covers

  • Transaction Pending - low gas, network congestion, validator delays
  • Transaction Failed - insufficient funds, smart contract reverts, gas exhausted, invalid parameters
  • Wrong Network - chain mismatches and environment (testnet vs production) errors
  • Confirmation Delays - congestion at the confirmation layer, validator issues, reorg protection periods

Skills Demonstrated

  • On-chain transaction debugging and trace analysis
  • Block explorer investigation (Etherscan, Basescan, Tenderly)
  • Gas mechanics and EIP-1559 fee model
  • ERC-20 token standard and smart contract interaction patterns
  • Multi-chain environment triage (EVM chains, chain ID verification)
  • API auth debugging and environment isolation
  • Structured root cause and escalation methodology
  • Idempotency and safe retry guidance

Reference Tools

  • Etherscan / Basescan / Solscan
  • Tenderly (transaction simulation and revert decoding)
  • Postman (API reproduction with sanitised payloads)
  • Block explorer gas trackers
  • Chain status pages and validator monitoring

Key Concepts

  • Transaction lifecycle: sign → broadcast → validate → include → confirm → finalise
  • Gas: base fee + priority tip; limit vs price distinction
  • Finality: Ethereum requires 2/3 supermajority validator attestation (~66.7%)
  • USDC: 6 decimal places on EVM chains (1 USDC = 1,000,000 raw units)

Transaction Pending

A pending transaction has been broadcast to the network but not yet included in a confirmed block. The cause determines whether the user needs to act or simply wait. Always check the block explorer first to confirm the transaction has been broadcast at all - a transaction with no explorer record has a different root cause entirely (RPC or broadcast failure).

Low Gas Price Set by User

Identify

  • Get the transaction hash from the customer and look it up on the relevant block explorer (Etherscan, Basescan, etc.)
  • Check the gas price paid in the transaction detail and compare it against the current network base fee via a gas tracker (e.g. Etherscan Gas Tracker)
  • Confirm the status shows Pending - not Failed. A pending status means the transaction is queued but unexecuted, distinguishing it from a reverted transaction
  • Ask whether the customer set a custom gas price manually in their wallet or API call, rather than using the dynamic estimate

Resolve

  • Advise the customer to use their wallet's speed up function, which re-broadcasts the transaction with a higher gas price at the same nonce - replacing the original in the mempool
  • If no speed-up option is available, they can submit a zero-value self-transfer with the same nonce and a higher gas price to displace the stuck transaction
  • For API-submitted transactions, resubmit with maxFeePerGas / gasPrice at least 10–12.5% higher than the original (Geth requires 10%; 12.5% is the safer cross-client minimum)
  • Confirm the replacement transaction is accepted and the original is dropped from the mempool before closing

Network Congestion

Identify

  • Check a gas tracker - confirm the current network base fee is significantly higher than the gas price the customer's transaction was submitted with
  • Check the mempool size: a large backlog of pending transactions confirms network congestion rather than a user-specific misconfiguration
  • Check whether multiple customers on the same chain are reporting similar delays - broad impact confirms congestion is the cause
  • Check the chain's status page for any active infrastructure incidents that may be compounding the congestion

Resolve

  • Communicate clearly that this is a network-level condition, not a platform or wallet issue, and set realistic resolution expectations
  • Advise the customer to wait if the use case is not time-sensitive - congestion periods typically resolve within minutes to hours
  • If urgency requires action, advise using the speed-up / replace flow with a gas price at or above the current network's recommended fast level
  • Recommend enabling dynamic gas pricing in future integrations rather than hardcoding a fixed gas price, to avoid recurrence

Validator Delays

Identify

  • Check the block explorer for block production rate - compare recent block timestamps against the chain's normal cadence. Unusually large gaps indicate a validator-layer issue
  • Check the chain's official status page or community channels for reported consensus or validator incidents
  • Confirm the transaction is visible on the explorer - if it has no record at all, the issue is at the RPC broadcast layer, not validators
  • Check whether the delay is affecting multiple senders across different wallets - this distinguishes a validator issue from a user-specific problem

Resolve

  • Communicate that validator delays are external infrastructure - resolution is outside platform control, and no user action will accelerate it
  • Monitor block production: once validators recover, pending transactions process in nonce order automatically - no resubmission needed in most cases
  • If the transaction was submitted via a specific RPC endpoint, try rebroadcasting through a different RPC provider in case the original node is degraded independently of the validator issue
  • Escalate to engineering if platform-operated infrastructure (e.g. RPC nodes, contract relay services) is affected alongside the validator issue

Transaction Failed

A failed transaction has been broadcast, reached the chain, and been rejected at execution time. Unlike a pending transaction, a failed status is final for that submission - the transaction will not retry automatically. Identifying the specific failure reason is the critical first step, as the resolution path differs significantly between insufficient funds, gas exhaustion, and smart contract reverts.

Insufficient Funds

Identify

  • Look up the wallet address on the block explorer and check its current token balance (e.g. USDC) and native gas token balance (ETH, MATIC, etc.) separately - these are distinct balances
  • Confirm the failure reason in the transaction detail - should show "Fail" with an out-of-funds or transfer-exceeds-balance error message
  • Determine whether the shortfall is in the transfer amount, the gas fee, or both - a customer can have USDC but insufficient ETH for gas, causing the same failure
  • For stablecoin payment platform flows, check whether the fiat deposit was received and settled before the on-chain operation was triggered

Resolve

  • If the token balance is short: advise the customer to fund the wallet with the required amount before retrying
  • If the native gas token balance is short: the customer must top up with ETH / MATIC / native token - holding stablecoin alone is not sufficient to pay gas on most chains
  • For platforms using gas abstraction or paymasters, verify the gas policy configuration is correct and active for this wallet before retrying
  • Once funded, advise the customer to retry. If using a platform API, submit with a new idempotency key to avoid conflicts with the failed request record

Smart Contract Revert

Identify

  • Find the transaction on the block explorer and check for a revert reason string in the detail (e.g. ERC20: transfer amount exceeds allowance)
  • If the revert reason is ABI-encoded, use a decoder tool such as Tenderly or Etherscan's built-in decoder to extract the human-readable message
  • Identify which contract and function reverted - was it the token contract, a third-party contract, or a platform contract? This determines whether the fix is in the customer's code or requires escalation
  • Check whether a required token approval step was skipped - when transferring ERC-20 tokens via a third-party contract, a prior approve() call is required and commonly missed

Resolve

  • Share the decoded revert reason with the customer and link it to the relevant field or contract requirement in the documentation
  • If the revert relates to allowance: the customer must call approve(spenderAddress, amount) on the token contract before the transfer call - this is a separate transaction
  • Advise the customer to simulate the corrected transaction via Tenderly before resubmitting - this confirms the fix is valid without spending real gas
  • If the revert is occurring inside platform-owned contracts rather than customer code, escalate to engineering with the full transaction hash, revert reason, and chain ID

Gas Exhausted

Identify

  • On the block explorer, compare Gas Used against Gas Limit for the failed transaction. If Gas Used equals Gas Limit exactly, the transaction ran out of gas mid-execution (out-of-gas failure)
  • Confirm this is an out-of-gas failure rather than a revert - both show as failed, but the diagnostic is Gas Used = Gas Limit for out-of-gas, whereas reverts typically use less than the full limit
  • Ask whether the customer set a custom gas limit that was lower than required, or relied on an RPC gas estimate without applying a buffer
  • Check whether the target contract has been recently updated - increased contract complexity raises the gas requirement and can invalidate previously working gas limits

Resolve

  • Advise the customer to increase the gas limit before retrying - a common safe starting point is 1.2–1.5× the eth_estimateGas result
  • Recommend calling eth_estimateGas with the exact calldata before every submission rather than using a cached or hardcoded limit
  • If using a gas abstraction layer or paymaster, verify the gas policy ceiling is sufficient for the complexity of the operation being performed
  • Note that gas paid on the failed transaction is not refunded - the computational work was performed up to the point of exhaustion. The customer must submit a fresh transaction

Invalid Parameters

Identify

  • Review the API request payload or transaction calldata for malformed values - common issues include incorrect address formats, wrong token decimal precision, or missing required fields
  • Check the platform API error response - 400-series errors typically include a structured body with field-level validation messages indicating the offending parameter
  • Verify the destination address format - EVM addresses are exactly 42 characters (0x prefix + 40 hex characters). Addresses of the wrong length or wrong character set indicate a formatting error
  • Confirm the chain ID in the request matches the chain where the wallet and token actually exist - a mismatch causes failures that can appear as invalid address errors

Resolve

  • Share the specific validation error message with the customer and map it to the relevant parameter in the API documentation
  • Verify token amounts use correct decimal precision: USDC uses 6 decimal places on EVM chains (1 USDC = 1000000 in raw units). Submitting 18-decimal amounts (as used for ETH) is a common integration error
  • Advise the customer to validate address format client-side before submission, including EIP-55 checksum validation for EVM addresses
  • Once corrected, resubmit with a new idempotency key to avoid the platform returning the cached result of the original failed request

Wrong Network

Wrong network errors are among the most disorienting for customers because the transaction often succeeds technically - the funds arrive somewhere, just not where they intended. The key insight is that the same wallet address exists independently on every EVM chain, so assets sent to the wrong chain are not lost - they exist at the correct address but on the wrong network. Recovery options depend on who controls the destination address.

Sending to an Address on the Wrong EVM Chain

Identify

  • Ask the customer to confirm which chain they sent from and which chain the recipient was expecting to receive on
  • Look up the destination address on both chain explorers - if assets arrived on the source chain's explorer but not on the recipient's expected chain, funds are present but on the wrong network
  • Confirm whether the destination wallet, exchange, or platform supports the source chain - many exchange deposit addresses only accept assets on one specific chain, and sending on another is a common user error
  • Check whether the receiving platform offers automatic multi-chain deposit detection - some platforms will credit cross-chain deposits after a delay without requiring manual recovery

Resolve

  • If the recipient controls the wallet address directly: they can add the source chain to their wallet and access the assets immediately - the same EOA address is valid on all EVM chains
  • If the recipient is a centralised exchange or custodian: advise the customer to contact the exchange's support team - many will manually credit cross-chain deposits, though this can take days and may incur fees
  • If recovery through the exchange is not possible, the customer may need to use an official cross-chain bridge to move the assets back to the intended chain. Advise using only official, audited bridges
  • For future transfers, advise the customer to always confirm the chain an exchange deposit address supports before sending. This error cannot be reversed by the sending platform

Testnet Address or Credentials Used in Production

Identify

  • Confirm which API environment the request was made against - check whether a sandbox or production API key was used, as these target different base URLs and different chain environments
  • Look up the wallet or contract address on both a mainnet and testnet block explorer (e.g. Etherscan for mainnet, Sepolia Etherscan for testnet) - a balance on testnet but not mainnet confirms the wrong environment
  • Check the chain ID in the request payload - Ethereum mainnet is chain ID 1; Sepolia testnet is 11155111. A chain ID mismatch confirms environment confusion
  • Review the API key in the developer dashboard - sandbox and production keys are clearly segmented and the key prefix typically indicates which environment it belongs to

Resolve

  • Confirm the customer has been issued a production API key - customers who have only completed sandbox onboarding will need to complete the production onboarding process before live transactions are possible
  • Ensure the customer is targeting the correct production API base URL - sandbox and production environments use different base URLs and keys are not cross-compatible
  • Audit the customer's configuration for hardcoded testnet chain IDs or contract addresses and replace them with mainnet equivalents. Note: Goerli testnet reached End of Life in January 2024 and is fully decommissioned - Sepolia is the current standard testnet
  • Recommend using environment variables rather than hardcoded values for all chain IDs, contract addresses, and API keys, to prevent this class of error recurring at the next deployment

Confirmation Delays

Confirmation delays occur after a transaction has been included in a block but before downstream systems (payment platforms, cross-chain bridges, exchange credits) recognise it as final. The critical distinction for support is between a transaction that is pending (not yet in a block) and one that is confirming (in a block, accumulating confirmations). The latter does not require any user action - it requires setting expectations.

Network Congestion at the Confirmation Layer

Identify

  • Verify the transaction has a block number on the explorer - this confirms it has been included and the delay is at the confirmation stage, not broadcast
  • Check how many confirmations have accumulated versus the number required by the receiving platform or bridge - most platforms publish their confirmation thresholds
  • Compare current average block time against the chain's normal cadence - slower blocks during congestion extend the real-world time between confirmations even when the count is progressing
  • Confirm whether the delay is affecting multiple transactions and senders on the same chain - broad impact confirms congestion; isolated delay may indicate a different cause

Resolve

  • Reassure the customer the transaction is secured in the chain - once included in a block, it cannot disappear or be lost during the confirmation period
  • Share the platform's required confirmation count and provide an estimated completion time based on current block times and the number of remaining confirmations
  • No action is required from the customer - confirmation accumulation is automatic and will complete without intervention
  • For future high-priority transactions, advise setting a higher gas price during known congestion windows to achieve faster block inclusion, which starts the confirmation countdown sooner

Validator Issues

Identify

  • Check the chain's validator participation rate - Ethereum's Casper FFG finality mechanism requires a 2/3 supermajority (~66.7%) of validator attestations. Participation below this threshold stalls finality
  • Check official chain status pages and community channels (e.g. Ethereum Foundation, chain-specific Discord servers) for reported consensus or validator incidents
  • Look at block production rate and missed slots on the explorer - large gaps or consecutive missed slots are the clearest signal of a validator-layer problem
  • Confirm whether the platform has raised an internal incident for the affected chain - if so, customer-facing communication should reference this

Resolve

  • Communicate clearly that this is a chain-level issue outside platform control - share public status page links so the customer can monitor progress directly
  • Once validators recover, finality resumes automatically and confirmation counts will begin accumulating again - no resubmission is required
  • If the validator issue is prolonged, check whether the customer's use case can be temporarily served by an alternative chain - for example, Base or Arbitrum in place of Ethereum mainnet, where confirmation times are faster by design
  • Escalate to engineering if platform-operated infrastructure (RPC nodes, bridge relay services, attestation services) is also impacted alongside the validator issue

Reorg Protection Waiting Periods

Identify

  • Confirm the transaction has a block number on the explorer but the downstream platform has not yet credited it - this is the standard signature of a reorg protection hold
  • Check the platform's required confirmation threshold for that specific chain - thresholds vary widely (e.g. 12 confirmations on Ethereum, fewer on faster chains), and this is the most common cause of unexplained delays on included transactions
  • Calculate the remaining confirmations needed and multiply by the current average block time to give the customer a concrete estimated wait time
  • Distinguish from a genuine chain reorganisation - if the block containing the transaction has been replaced by a competing chain, the transaction reverts to pending status and the explorer will reflect this within minutes

Resolve

  • Explain that this is expected platform behaviour, not an error - confirmation thresholds exist to protect against the small probability of chain reorganisations reversing a credited transaction
  • Provide the customer with the exact confirmation count required and the estimated time remaining - specific information is far more useful than a generic "please wait" response
  • If a genuine reorg has occurred: the transaction will be re-included in the canonical chain automatically in most cases - a new submission is usually not required, and the original transaction remains valid
  • For latency-sensitive use cases, recommend evaluating chains with shorter confirmation requirements (Base, Arbitrum, Polygon) where finality is faster and platform credit thresholds are proportionally lower

Key Principles for Blockchain Support

Blockchain support differs from traditional software support in one fundamental way: you have an independent source of ground truth. The block explorer does not lie. Before forming any hypothesis, the first action is always to look up the transaction hash and establish what the chain actually recorded - not what the customer believes happened, and not what the application layer reported.

The second consistent theme across all the failure patterns above is the importance of layer identification before action. Is the issue at the API layer, the broadcast layer, the validation layer, the on-chain execution layer, or the confirmation layer? Applying the wrong fix - for example, advising a customer to resubmit when the original transaction is still confirming - can compound the problem and erode trust.

Finally: irreversibility changes the stakes. A mis-directed transaction cannot be recalled. A gas fee on a failed transaction is not refunded. In blockchain support, advising customers to act before the root cause is understood carries real financial risk. The structured identify-before-resolve approach in this guide reflects that.
