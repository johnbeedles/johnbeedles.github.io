On-Chain Failure Troubleshooting Guide

A practical support engineer reference covering the most common on-chain failure patterns — from pending and failed transactions through to nonce conflicts, API-layer async failures, confirmation delays, and compliance escalation. Each failure mode includes structured identification steps and a clear resolution path, built from hands-on blockchain infrastructure support experience.

What Makes Blockchain Support Different

Blockchain support is distributed-systems debugging with financial stakes and irreversible state changes. That combination produces failure patterns and investigation requirements that don't appear in traditional SaaS support environments.

Unique Challenges

  • Transactions are irreversible. A misdirected payment or an incorrectly advised retry cannot be recalled. Every action recommendation carries direct financial risk for the customer.
  • Failure states are layered. "Transaction not arrived" could mean API rejection, broadcast failure, mempool drop, on-chain revert, confirmation delay, platform processing lag, or compliance hold - each with a different fix. Jumping to solutions before identifying the layer compounds the problem.
  • Finality is a spectrum, not a binary. A transaction included in a block is not automatically settled. Short reorgs can orphan recently included blocks. Platform credit thresholds exist precisely because "included" and "settled" are different states.
  • The same wallet address means different things on different chains. An EVM address on Ethereum and the identical address string on Base are entirely separate accounts. Chain ID verification is as important as address verification.
  • Block explorers represent chain state - they are not chain state. Explorers index the chain and can lag by seconds to minutes. Stale indexing, RPC provider divergence, and mempool inconsistencies between nodes mean a single explorer view is a representation, not the source of truth.

How This Changes the Support Approach

  • Establish the failure layer before acting. API layer, broadcast layer, mempool, on-chain execution, or confirmation and settlement - the answer changes everything about what comes next.
  • Gather on-chain evidence independently. Do not rely solely on what the customer reports or what the application layer logged. Verify the transaction hash directly on the chain and cross-reference with structured logs and distributed traces.
  • Know when not to advise action. A confirming transaction should not be resubmitted. A compliance-held transaction should not be retried. Incorrect advice at these moments directly damages the customer.
  • Distinguish platform failures from chain failures. Validators going offline, network congestion, and reorgs are outside platform control. Webhook failures, RPC degradation, and API bugs are not. The escalation path and customer communication differ entirely.
  • Compliance intersects with operations. Not every stuck transaction is a technical failure. Sanctions screening holds, AML-triggered pauses, and fraud flags produce states that look like technical errors but require a fundamentally different response.

About This Guide

This reference organises common blockchain support failure patterns by category, with step-by-step identification and resolution guidance for each. It reflects a structured investigation approach built on layer identification, evidence gathering, and operational discipline - establishing what the chain actually recorded before forming any hypothesis about what went wrong.

Real-world blockchain support investigations are frequently messier than clean documentation suggests: RPC providers return conflicting state, explorers lag behind the live chain, async webhooks arrive out of order, and nonce gaps stall entire transaction queues silently. The sections below are written with that operational reality in mind.

Key Concepts

  • Transaction lifecycle: sign → broadcast → mempool → validate → include → confirm → finalise
  • Gas: base fee + priority tip; limit vs price; EIP-1559 vs legacy
  • Nonce: sequential per-address counter; gaps stall all subsequent transactions
  • Finality: Ethereum requires 2/3 supermajority validator attestation (~66.7%)
  • USDC: 6 decimal places on EVM chains (1 USDC = 1,000,000 raw units)
  • Explorer lag: explorers index chain data - they represent state, they do not define it

Transaction Pending

A pending transaction has been broadcast to the network but not yet included in a confirmed block. Always verify the transaction is visible on the block explorer first - a transaction with no explorer record has not been successfully broadcast and requires a different investigation path (RPC failure, signing error, or submission error) than the scenarios below.

Low Gas Price Set by User

Identify

  • Get the transaction hash from the customer and look it up on the relevant block explorer (Etherscan, Basescan, etc.)
  • Check the gas price paid in the transaction detail and compare against the current network base fee via a gas tracker - a paid price below the current base fee confirms the cause
  • Confirm the status shows Pending - not Failed. Pending means queued but not executed; Failed means it reached the chain and was rejected. Different states, different fixes
  • Ask whether the customer set a custom gas price manually, or used a hardcoded value that was valid at integration time but has since become stale relative to current network conditions

Resolve

  • Advise the customer to use their wallet's speed up function, which re-broadcasts the transaction with a higher gas price at the same nonce, replacing the original in the mempool
  • If no speed-up option exists, submit a zero-value self-transfer at the same nonce with a higher gas price to displace the stuck transaction
  • For API-submitted transactions, resubmit with maxFeePerGas / gasPrice at least 10–12.5% higher than the original (Geth requires 10% minimum; 12.5% is the safer cross-client standard)
  • Confirm the replacement is accepted and the original dropped. Also verify the customer has not introduced a nonce gap in the process - see the Nonce & Mempool section below

Network Congestion

Identify

  • Check a gas tracker - confirm the current network base fee is significantly higher than the gas price the customer's transaction used
  • Check the mempool size: a large backlog of pending transactions confirms network-wide congestion rather than a user-specific misconfiguration
  • Check whether multiple customers on the same chain are reporting similar delays at the same timestamp - broad impact confirms congestion is the cause
  • Note that different RPC providers may report different mempool sizes - if one provider shows normal conditions, check a secondary provider before ruling congestion out

Resolve

  • Communicate clearly that this is a network-level condition, not a platform or wallet issue, and set realistic expectations based on current mempool depth
  • Advise the customer to wait if the use case is not time-sensitive - congestion typically resolves within minutes to a few hours
  • If urgency requires action, advise the speed-up / replace flow with a gas price at or above the network's current recommended fast level, not the average
  • Recommend enabling dynamic gas pricing in future integrations - hardcoded gas prices are the root cause of the majority of user-originated pending transaction issues

Validator Delays

Identify

  • Check the block explorer for block production rate - compare recent block timestamps against the chain's normal cadence; gaps of multiple times the expected block time indicate a validator-layer issue
  • Check the chain's official status page or community channels for reported consensus or validator incidents
  • Confirm the transaction is visible on the explorer - if there is no record at all, the issue is at the RPC broadcast layer, not validators
  • Check whether the delay affects multiple senders and wallets - this distinguishes a validator issue from a nonce gap or user-specific problem that coincidentally occurs during a slow block

Resolve

  • Communicate that validator delays are external infrastructure - no user-side action will accelerate block production
  • Once validators recover, pending transactions process in nonce order automatically - resubmission is generally not required and risks creating nonce conflicts
  • If submitted via a specific RPC endpoint, try rebroadcasting through a different RPC provider - node-level degradation can sometimes be mistaken for broader validator issues
  • Escalate to engineering if platform-operated infrastructure (RPC nodes, relay services) is affected - distinguish clearly between chain-level and platform-level impact in the escalation note

Nonce & Mempool Complexity

Nonce and mempool issues are among the most common causes of silently stalled transaction queues in production wallet infrastructure, and one of the most frequently misdiagnosed. Because the symptom looks identical to network congestion or low gas, the nonce state must always be verified independently before advising any retry or replacement action.

Nonce Gaps

Identify

  • Query the wallet address using eth_getTransactionCount to retrieve the on-chain nonce, then compare against the nonce of the stuck transaction - if there is a gap between the two, no transactions will be processed until it is filled
  • If a pending transaction has a nonce higher than the on-chain expected nonce and no transaction fills the gap, the network will not process the queued transaction regardless of gas price
  • Check whether a previous transaction was dropped from the mempool without being replaced - transactions can be silently evicted by nodes after extended pending periods, particularly on congested networks, without any notification to the sender
  • In high-throughput wallet infrastructure, check whether parallel transaction submission with non-sequential nonce assignment caused the gap - common in automated payment pipelines submitting multiple transactions concurrently

Resolve

  • Fill the gap by submitting a transaction at the missing nonce - a zero-value self-transfer is sufficient if no real operation is needed at that position, purely to unblock the queue
  • Before submitting the gap-filler, confirm the dropped transaction is no longer pending on multiple RPC providers - acting on stale data from a single node is a common source of double-submission errors
  • Once the gap is filled and confirmed, subsequent transactions should process in sequence without further intervention - monitor the queue to confirm the backlog drains
  • For automated pipelines, advise implementing nonce management with a per-wallet locking mechanism to prevent concurrent submissions from creating gaps under load

Replacement Transaction Failures & RPC Inconsistency

Identify

  • If a replacement transaction returns a "replacement transaction underpriced" error, the bump did not meet the minimum threshold - the original is still pending and the replacement was rejected outright
  • Check whether the customer is querying different RPC providers for nonce and pending state - providers can have divergent mempool views, causing a transaction to appear dropped on one endpoint while still live on another
  • If a transaction appears replaced successfully but the original later confirms, both transactions were submitted at the same nonce - check both hashes on the explorer to determine which was included and which orphaned
  • Watch for nonce reuse errors in the API response - these indicate the customer's nonce tracking is out of sync with on-chain state, typically caused by a failed transaction that did not advance the nonce as expected

Resolve

  • For underpriced replacement errors: resubmit with at least 12.5% higher gas price than the current pending transaction - not the original submission, as prior replacement attempts may have already raised the effective price
  • For RPC inconsistency: verify pending state across at least two independent RPC providers before advising any replacement - acting on stale data from a single node is a consistent source of double-submission incidents
  • If both a replacement and original have confirmed: do not advise further retries. Escalate with both transaction hashes - the operations team needs to determine which is canonical and whether reconciliation is required
  • For nonce tracking issues in automated systems, resynchronise by calling eth_getTransactionCount with the pending parameter before the next submission, and implement per-wallet nonce locking going forward

In Practice: A Realistic Nonce Incident

A typical production nonce incident does not present as a clean single failure. A more realistic pattern: a customer reports three transactions submitted in quick succession have been pending for 45 minutes. The block explorer shows all three as pending. Gas prices look reasonable. The network is not congested.

Querying eth_getTransactionCount reveals the on-chain nonce is two behind the first of the three visible transactions. A transaction submitted earlier that day — not mentioned by the customer - was silently dropped from the mempool after an RPC provider restart. The customer's wallet continued incrementing nonces locally, unaware that the dropped transaction left a gap. All three visible transactions are valid and correctly priced, but none will process until the gap nonce is filled.

The resolution is a zero-value gap-filler at the missing nonce, followed by monitoring to confirm the queue drains in order. The investigation took longer than expected because the dropped transaction appeared in no log the customer could access - only the on-chain nonce query exposed it. This is why nonce state must always be checked independently, not inferred from what the customer reports.

Transaction Failed

A failed transaction has been broadcast, reached the chain, and been rejected at execution time. Unlike a pending transaction, this status is final for that submission - it will not retry automatically. Identifying the specific failure reason is critical before advising any action, as the resolution path differs significantly between the cases below. Do not advise resubmission until the root cause is confirmed.

Insufficient Funds

Identify

  • Look up the wallet address on the block explorer and check its current token balance (e.g. USDC) and native gas token balance (ETH, MATIC, etc.) separately - either can independently cause failure
  • Confirm the failure reason in the transaction detail - should show a transfer-exceeds-balance or out-of-funds error. Some explorers surface this inline; others require Tenderly to decode
  • Determine whether the shortfall is in the transfer amount, the gas fee, or both - a customer can hold significant stablecoin while having insufficient native token for gas, producing an identical failure signature
  • For payment platform flows, check whether the fiat deposit was received and settled on-chain before the operation was triggered - settlement timing mismatches are a common cause of apparently unexplained shortfalls

Resolve

  • If the token balance is short: advise the customer to fund the wallet with the required amount and confirm the deposit has settled before retrying
  • If the native gas token is short: the customer must top up with the native token - holding stablecoins alone is not sufficient to pay gas without an active gas abstraction layer
  • For platforms using gas abstraction or paymasters, verify the gas policy is active, correctly scoped to this wallet, and has sufficient credit before advising retry
  • Once funded, retry with a new idempotency key if using a platform API - reusing the original request ID can return a cached failure response depending on platform implementation

Smart Contract Revert

Identify

  • Find the transaction on the block explorer and check for a revert reason string (e.g. ERC20: transfer amount exceeds allowance). Not all explorers surface this - use Tenderly if the reason is absent
  • If the revert reason is ABI-encoded hex, use Tenderly's revert decoder or Etherscan's built-in ABI decoder to extract the human-readable message before sharing with the customer
  • Identify which contract and function reverted - token contract, third-party protocol, or platform-owned contract? This determines whether the fix is in the customer's integration or requires internal escalation
  • Check whether a required ERC-20 token approval was skipped - a prior approve() call is required when transferring tokens via a third-party contract. This is the single most common smart contract revert in production integrations

Resolve

  • Share the decoded revert reason with the customer and link to the relevant documentation requirement - most standard ERC-20 revert reasons are self-explanatory once decoded
  • If the revert is an allowance issue: the customer must call approve(spenderAddress, amount) on the token contract first - this is a separate on-chain transaction that must be confirmed before retrying the transfer
  • Advise the customer to simulate the corrected transaction in Tenderly before resubmitting - this validates the fix without spending gas and surfaces any secondary revert conditions before they hit production
  • If the revert is inside platform-owned contracts, do not ask the customer to retry. Escalate to engineering with the transaction hash, decoded revert reason, and chain ID - this is a potential platform bug

Gas Exhausted

Identify

  • On the block explorer, compare Gas Used against Gas Limit - if Gas Used equals Gas Limit exactly, the transaction ran out of gas mid-execution. This is the most reliable diagnostic signal for OOG failure
  • Confirm this is OOG rather than a revert - reverts typically consume less than the full limit (the EVM halts at the revert opcode). Gas Used equals Gas Limit means OOG; Gas Used significantly below Gas Limit means revert
  • Ask whether the customer set a custom gas limit or relied on an unmodified eth_estimateGas result. Estimates are calculated against current chain state at estimation time - if state changes between estimation and submission, the estimate may be insufficient
  • Check whether the target contract has been recently upgraded - proxy contracts can increase gas requirements significantly after an upgrade, invalidating previously working limits

Resolve

  • Advise the customer to increase the gas limit - a common starting point is 1.2–1.5× the eth_estimateGas result, providing buffer for state-dependent gas variation
  • Recommend calling eth_estimateGas with the exact calldata immediately before each submission rather than caching an estimate - gas requirements for the same operation can vary between blocks
  • If using a gas abstraction layer or paymaster, verify the gas ceiling in the policy is sufficient for the current operation - policies set at integration time may not account for contract upgrades
  • Note clearly that gas paid on the failed transaction is not refunded - the EVM performed computation up to the exhaustion point. The customer must submit a fresh transaction with the corrected limit

Invalid Parameters

Identify

  • Review the API request payload or transaction calldata for malformed values - wrong address formats, incorrect token decimal precision, missing required fields, or zero-value amounts where non-zero is required
  • Check the platform API error response body - 400-series errors from well-designed APIs include field-level validation messages that identify the offending parameter directly
  • Verify the destination address format - EVM addresses are exactly 42 characters (0x prefix + 40 hex characters). Wrong length, non-hex characters, or missing 0x prefix all produce identical error messages despite being different errors
  • Confirm the chain ID matches the chain where the wallet and token exist - a chain ID mismatch sometimes produces an "invalid address" error rather than a "wrong chain" error, which misdirects initial diagnosis

Resolve

  • Share the specific validation error and field reference with the customer and link to the relevant API documentation section
  • Verify token amounts use correct decimal precision: USDC uses 6 decimal places on EVM chains (1 USDC = 1000000 raw units). Submitting amounts using 18 decimals - as used by ETH and many other tokens - is a very common integration error
  • Advise adding client-side address validation including EIP-55 checksum verification before submission - catching format errors before they reach the API reduces round-trip debugging time significantly
  • Once corrected, resubmit with a new idempotency key - reusing the original key may return a cached error response depending on how the platform handles idempotency for validation failures

Wrong Network

Wrong network errors are among the most disorienting for customers because the transaction often succeeds technically - funds arrive somewhere, just not where intended. The key operational insight is that the same wallet address exists independently on every EVM chain, so assets sent to the wrong chain are not lost - they are at the correct address on the wrong network. Recovery depends entirely on who controls the destination address.

Sending to an Address on the Wrong EVM Chain

Identify

  • Ask the customer to confirm which chain they sent from and which chain the recipient expected to receive on - do not assume these match based on the customer's initial description
  • Look up the destination address on both chain explorers independently - confirm assets arrived on the source chain and check whether any balance exists on the chain the recipient was expecting
  • Confirm whether the destination wallet, exchange, or platform supports the source chain - many exchange deposit addresses accept only one specific chain and the network does not reject sends from other chains at the protocol level
  • Check whether the receiving platform offers automatic multi-chain deposit detection - some platforms credit cross-chain deposits after a manual review period; always check this before advising a bridge-based recovery

Resolve

  • If the recipient controls the address: they can add the source chain to their wallet and access the assets immediately - the same EOA address is valid on all EVM chains and the private key controls it on each
  • If the recipient is a centralised exchange: advise contacting the exchange's support team - many will manually credit cross-chain deposits, though the process can take days and success is not guaranteed for all chains
  • If exchange recovery is unavailable, the customer may need an official, audited cross-chain bridge - always advise using only the chain's officially recommended bridge, as unofficial bridges carry significant security risk
  • For future prevention: advise the customer to always verify the chain tag shown on an exchange deposit address before sending. This error cannot be reversed by the sending platform

Testnet Credentials or Addresses Used in Production

Identify

  • Confirm which API environment the request targeted - sandbox keys submitted against production endpoints consistently produce 401 errors; this is the most common symptom
  • Look up the wallet or contract address on a testnet block explorer (Sepolia Etherscan) - a balance present on testnet but not mainnet confirms the customer has been working in the wrong environment. Note: Goerli reached End of Life in January 2024 and is fully decommissioned; Sepolia is the current standard testnet
  • Check the chain ID in the request payload - Ethereum mainnet is chain ID 1; Sepolia testnet is 11155111. A mismatch here definitively confirms environment confusion
  • Confirm which environment the customer believes they are targeting versus which they are actually hitting - the gap between these two answers is often wider than expected

Resolve

  • Confirm the customer has a production API key - sandbox-only customers must complete production onboarding before live transactions are permitted
  • Ensure the customer is using the correct production API base URL - sandbox and production environments use different base URLs; keys are not cross-compatible
  • Audit the customer's config for hardcoded testnet chain IDs, contract addresses, or RPC endpoints - all must be replaced with mainnet equivalents. Testnet contracts are not deployed on mainnet
  • Recommend environment variables for all chain IDs, contract addresses, RPC URLs, and API credentials - hardcoded values are the primary cause of testnet/production confusion at deployment

API-Layer & Async Failures

Not all blockchain support issues originate on-chain. A significant category of failures occurs in the API and asynchronous processing layer - rate limiting, webhook delivery problems, async job state mismatches, and eventual consistency issues that cause platform state to diverge from on-chain reality. These are often harder to diagnose because they produce no transaction hash, and the customer cannot easily distinguish a platform processing issue from an on-chain one.

Rate Limiting (429 Errors)

Identify

  • Check the HTTP response status code in the customer's API logs - a 429 confirms rate limiting rather than an authentication or validation failure
  • Check the response headers - Retry-After and X-RateLimit-* headers indicate the limit type (per-second, per-minute, per-key) and the reset window. These should be the first data requested from the customer
  • Identify the request pattern - burst pattern (a batch job firing all at once) or consistent throughout the day? Burst patterns suggest missing backoff logic; consistent patterns suggest volume approaching tier limits
  • Check whether the customer is using a single API key across multiple services - shared keys aggregate consumption and can cause rate limiting that appears unrelated to any single service

Resolve

  • Advise implementing exponential backoff with jitter on all API requests - retrying immediately after a 429 sustains the rate limit violation rather than resolving it
  • Recommend honouring the Retry-After header value rather than using a fixed retry interval - this aligns retries with the actual reset window
  • For batch processing, advise spreading requests across the rate limit window with a controlled dispatch rate rather than submitting concurrently - this resolves burst-pattern 429s without a tier upgrade in most cases
  • If legitimate traffic consistently exceeds the current tier, escalate to account management with documentation of the customer's request pattern and business use case

Webhook Delivery Failures

Identify

  • Check the platform's webhook delivery logs - confirm whether the event was dispatched, how many delivery attempts were made, what HTTP response code the customer's endpoint returned, and whether the retry queue is exhausted
  • If the event shows as delivered but the customer reports non-receipt, request the customer endpoint's access logs for the delivery timestamp - the event may have been received but discarded, failed signature verification, or consumed by a different process
  • Check whether the customer is performing webhook signature verification and whether it is passing - failed signature checks cause silently discarded events that are indistinguishable from undelivered events from the customer's side
  • For duplicate event reports, check whether the endpoint is returning non-2xx responses intermittently - if the handler processes the event before the response is sent, platform retries produce duplicates

Resolve

  • For undelivered events: confirm the endpoint URL is correctly registered, publicly reachable, and returning 2xx. A temporary outage during delivery can exhaust the retry queue - check whether the event can be manually replayed from the dashboard
  • For signature verification failures: confirm the customer is using the correct webhook secret, computing HMAC-SHA256 over the raw request body (not a parsed or re-serialised version), and comparing against the correct header
  • For duplicate event handling: advise implementing idempotent event processing using the event ID as a deduplication key - the platform cannot guarantee exactly-once delivery; consumer-side idempotency is the correct architectural approach
  • If webhook events are consistently delayed or failing across multiple customers, escalate to engineering with affected event IDs, delivery attempt logs, and timestamps - this may indicate a platform-side queue issue

Async Job States & Eventual Consistency

Identify

  • When a customer reports a transfer as "stuck" but there is no failed transaction on-chain, check the platform's async operation status - the on-chain transaction may be confirmed while platform-side processing is still reconciling
  • Compare the on-chain transaction timestamp against the platform's last status update - a significant gap indicates platform-side processing lag rather than an on-chain issue
  • Check whether the customer is polling a status endpoint immediately after submission - async operations are not complete at submission time, and an "in progress" status is not a failure
  • For balance discrepancies between on-chain state and platform balance, check whether a reconciliation job is scheduled or in progress - batch reconciliation platforms can show stale balances during high-volume periods

Resolve

  • Establish the expected processing SLA for the operation type and confirm the customer's wait time against it - do not treat an operation as failed until it exceeds the documented window
  • Advise using webhooks rather than polling where the platform supports both - polling introduces race conditions with eventual consistency windows and increases unnecessary API load
  • If platform state has not updated after the expected window, escalate with the on-chain transaction hash, operation ID, and timestamp - engineering can inspect the processing queue and identify whether the job has stalled
  • Do not advise the customer to submit a corrective transaction to fix a balance discrepancy until reconciliation state is confirmed - submitting against a stale balance can create a double-credit or overpayment that is significantly harder to unwind

Confirmation Delays

Confirmation delays occur after a transaction has been included in a block but before downstream systems recognise it as settled. Confirming transactions generally require no user action - the primary support task is verifying the confirmation count is progressing and setting accurate expectations about when the threshold will be reached.

Network Congestion at the Confirmation Layer

Identify

  • Verify the transaction has a block number on the explorer - this is the critical first check. A block number confirms the transaction is included and the delay is at the confirmation stage, not broadcast
  • Check how many confirmations have accumulated versus the number required by the receiving platform - most platforms publish their thresholds, and this comparison usually resolves the customer's concern immediately
  • Compare current average block time against the chain's normal cadence - slow blocks during congestion extend the real-world time between confirmations even when the count is progressing correctly
  • If a single transaction appears to lag while others confirm normally, consider whether this is an explorer indexing delay rather than a genuine chain issue - querying the transaction directly via RPC can confirm whether the confirmation count is accurate

Resolve

  • Reassure the customer that the transaction is recorded in the chain and progressing normally - a transaction with a block number is in the canonical chain. Note that very recently included blocks can be reorganised in rare cases, but this is uncommon and self-resolving
  • Share the platform's required confirmation count and an estimated completion time based on current block times - specific numbers are far more useful than a generic "please wait"
  • No action is required - confirmation accumulation is automatic once the transaction is included
  • For future high-priority transactions, advise setting a higher gas price during congestion windows to achieve faster inclusion, which starts the confirmation countdown sooner

Validator Issues

Identify

  • Check the chain's validator participation rate - Ethereum's Casper FFG mechanism requires a 2/3 supermajority (~66.7%) of validator attestations. Participation below this threshold stalls finality even when blocks continue to be produced
  • Check official chain status pages and community channels for reported consensus incidents - validator issues at scale are typically announced quickly on official channels
  • Look at block production rate and missed slots on the explorer - consecutive missed slots or large block time gaps are the clearest on-chain signal of a validator-layer problem
  • Confirm whether the platform has raised an internal incident for the affected chain - customer-facing communications should reference this and avoid committing to restoration timelines not yet confirmed internally

Resolve

  • Communicate clearly that this is a chain-level issue outside platform control - share public status page links so the customer can monitor independently
  • Once validators recover, finality resumes automatically - no resubmission is required, and resubmission during a validator incident risks nonce conflicts
  • If the issue is prolonged, assess whether an alternative chain can temporarily serve the customer's use case - Base or Arbitrum rather than Ethereum mainnet, where applicable
  • Escalate to engineering if platform infrastructure is also impacted - distinguish clearly between what is the chain's issue and what is additionally the platform's issue

Reorg Protection Waiting Periods

Identify

  • Confirm the transaction has a block number but the downstream platform has not yet credited it - this is the standard signature of a reorg protection hold, and it is expected behaviour, not a failure
  • Check the platform's required confirmation threshold for the specific chain - thresholds vary widely (12+ on Ethereum mainnet, fewer on L2s), and most unexplained delays on included transactions trace to this explanation
  • Calculate remaining confirmations and multiply by current average block time - this converts a frustrating wait into a predictable one, which is the most effective customer communication in this scenario
  • Distinguish from a genuine chain reorganisation - if the block containing the transaction is replaced, the transaction reverts to pending on the explorer and may temporarily disappear from history before being re-included

Resolve

  • Explain that this is expected platform behaviour - confirmation thresholds protect against the financial risk of crediting a transaction that may still be reorganised out of the canonical chain
  • Provide the exact confirmation count required and estimated completion time - generic "please wait" responses are the most common cause of repeat contacts on this issue type
  • If a genuine reorg has occurred: the transaction will typically be rebroadcast and re-included by the original sender's node in most cases, but this is not guaranteed. If it does not reappear within a reasonable window, the customer may need to resubmit
  • For latency-sensitive use cases, recommend evaluating chains with shorter confirmation thresholds - Base, Arbitrum, and Polygon offer faster finality and proportionally lower platform credit thresholds

Compliance & Security Escalation

In stablecoin and payments infrastructure, some operational states that resemble technical failures are compliance or security holds. Treating a sanctions screening hold as a bug, or advising a retry on a transaction flagged for AML review, can have serious regulatory consequences. Support engineers in fintech and Web3 infrastructure must know where the technical investigation stops and the compliance escalation begins.

Sanctions Screening & AML Holds

Identify

  • If a transfer is blocked with no corresponding on-chain failure, check the platform's transfer status - a compliance-held transaction will show a status distinct from technical failure states (e.g. pending_review or held)
  • Check whether the account's KYC or verification status is complete - incomplete onboarding, expired verification, or outstanding document requests block transactions silently from the customer's perspective
  • Note whether the transaction involves an address flagged by chain analytics tooling (e.g. Chainalysis, Elliptic) - such flags can trigger automatic holds that look like platform errors but are compliance decisions
  • Do not attempt to diagnose the specific compliance reason from support tooling - compliance case details are restricted to the compliance team and should not be discussed with the customer beyond acknowledging a review is in progress

Resolve

  • Do not advise the customer to retry a transaction that may be under compliance review - retrying a potentially sanctioned transaction compounds the regulatory issue and creates additional records that complicate the review
  • Escalate immediately to the compliance or trust and safety team with the transaction ID, account ID, and relevant context - do not route compliance holds through engineering channels
  • Communicate to the customer that the transaction is under review and that the relevant team will be in contact - do not disclose the review reason, the reviewing team, or expected timelines unless explicitly cleared to do so
  • Document the escalation in the incident record with a clear audit trail - compliance escalations require separate documentation from standard technical incident notes

Compromised Wallet or Suspected Fraud

Identify

  • If a customer reports unauthorised transactions from their wallet, treat this as a security incident immediately - do not investigate as a standard technical failure
  • Check the transaction history on the block explorer for the affected address - look for unexpected outflows, token approvals to unknown contracts, or interactions with known drainer or phishing contract addresses
  • Determine whether the customer uses a custodial or non-custodial wallet - the platform's ability to act and the response path differ significantly between these two models
  • Check whether the customer has recently signed an approval they may not have fully understood - unlimited token approvals granted to malicious contracts are a primary vector for wallet drains

Resolve

  • Advise the customer to immediately revoke all token approvals for unfamiliar contracts using a tool such as revoke.cash - this stops ongoing drain access even if the initial compromise has already occurred
  • If the wallet is custodial and the platform can freeze activity: escalate to the security or operations team immediately for a platform-level account freeze pending investigation
  • Advise the customer to move remaining assets to a new, uncompromised wallet as a priority - do not wait for the investigation to complete before migrating funds, as the compromised key remains active until assets are moved
  • Open a formal security incident rather than a standard support ticket - compromised wallet cases require a separate investigation trail, security team coordination, and potentially regulatory notification depending on the platform and jurisdiction

Operational Principles

The failure patterns in this guide all share a common investigation logic. These are the principles I apply consistently across on-chain support cases, regardless of which specific failure type is presenting.

Investigation Discipline

  • Chain state is the ground truth. Explorers are representations of it. Block explorers index chain data and can lag, diverge between providers, or temporarily misrepresent mid-reorganisation state. When explorer data and customer-reported data conflict, query the chain directly via RPC before drawing any conclusion.
  • Identify the failure layer before acting. API rejection, broadcast failure, mempool drop, on-chain revert, confirmation hold, platform processing lag, and compliance hold all present as "transaction not arrived." Each has a different fix. Applying the wrong one wastes time and can compound the original problem.
  • Gather evidence independently. Do not rely solely on what the customer reports or what the application layer logged. Cross-reference the transaction hash on the chain, verify distributed traces with the correlation ID, and check webhook delivery records separately from customer-reported receipt.
  • Incomplete and conflicting telemetry is normal. Real investigations frequently involve contradictory signals: one RPC provider shows pending, another shows dropped; the explorer shows inclusion while the platform shows processing; delivery logs show success while the customer reports non-receipt. Hold multiple hypotheses and eliminate them systematically - do not lock onto the first consistent explanation.

Escalation & Risk Management

  • Irreversibility changes the stakes. A misdirected transaction cannot be recalled. Gas on a failed transaction is not refunded. An incorrectly advised retry during a compliance hold creates regulatory exposure. In blockchain support, acting before the root cause is confirmed carries direct financial and legal risk. Speed is not a virtue when the action is irreversible.
  • Know when not to advise action. A confirming transaction should not be resubmitted. A compliance-held transaction should not be retried. A nonce gap should not be filled without confirming the dropped transaction is truly gone. The most impactful thing a support engineer sometimes does is stop a customer from making a problem significantly worse.
  • Distinguish platform failures from chain failures precisely. Validator outages, congestion, and reorgs are outside platform control. Webhook failures, RPC degradation, and API bugs are not. Customer communication, escalation path, and SLA commitment differ entirely between these categories - conflating them erodes customer trust and misdirects engineering effort.
  • Escalation quality matters more than escalation speed. An escalation with a transaction hash, decoded revert reason, reproduction steps, correlation ID, and a clear hypothesis is resolved in a fraction of the time of one that says "customer reports transaction failed." The investigation done before escalation determines how quickly the issue gets fixed.
